This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Website + admin panel for "Centro Estético Manuj" (professional makeup artist / cosmetologist), built with Next.js App Router and Supabase (Postgres + Auth + Storage). Two systems share the same database:

1. **Public site + booking** (`/`, `/galeria`, `/reservar`) — a marketing site whose content (carousel, services, gallery, about, mission/vision, footer, promotions) is **not hardcoded**: it's fetched from Supabase and managed through an admin CMS. `/reservar` is a public appointment-request wizard; appointments are never auto-confirmed, Manu confirms manually from the admin.
2. **Admin panel** (`/admin/*`, single authenticated user, no roles) — appointment inbox/calendar/schedule, service catalog, finances, client history + loyalty, and the content CMS (`/admin/contenido`).

**Read `docs/REFERENCIA-CMS-Y-ADMIN.md` and `docs/PRD-agendamiento.md` before making non-trivial changes** — they cover the full data model, every Server Action, every route, and the design decisions behind them (in Spanish, like all `docs/*.md` in this repo). The various `docs/HANDOFF-*.md` and `docs/PRD-*.md` files are narrative session logs kept for history; the two files above are the up-to-date reference and should be trusted over any handoff if they disagree.

The repo originates from and stays in sync with a [v0.dev](https://v0.dev) project (see README.md) for the original scaffold — v0 is no longer the source of truth for content (that moved to the CMS), but component scaffolding conventions from it still apply.

## Database / migrations

**There are TWO separate Supabase projects** — dev (`rtmuaeonmqadbezygfrv`, what `.env.local` points at) and production (`rlpwmheokkrttxyfusyp`, what the Vercel env vars point at, serving `centroesteticomanuj.com`). They share nothing: separate data, separate Auth users, separate Storage buckets. **Every migration has to be run twice, once per project.** Running it only in dev and then testing in production produces errors that look like code bugs and aren't — that's exactly what happened with `0013`. For the same reason, **a migration must never seed a hardcoded Storage URL**: it would make production serve that file from the dev project's bucket (see the comment in `0015`, which was rewritten for this).

Supabase migrations live in `supabase/migrations/`, numbered and run manually (no CLI/CI hooked up from this dev environment — paste each new one into Supabase Studio's SQL Editor). They're additive from `0002` on (no `drop`s) since both projects have real data, and should be re-runnable: use `if not exists` / `create or replace` / `on conflict do nothing`, and **put `drop policy if exists` before every `create policy`** (a `create table if not exists` will happily reach an already-existing policy on a second run and fail there). **After writing a new migration, ask the user to run it before relying on the new schema** — this has been the pattern for every migration in this project so far.

`SUPABASE_SERVICE_ROLE_KEY` in `.env.local` allows scripting one-off data work (content migrations, verification, temp admin users for testing) directly against the dev project — see `scripts/migrate-cms-content.mjs` for the pattern. Always clean up temp scripts/users/test rows after using them.

## Notifications (`/admin/notificaciones`)

Email via **Resend**; WhatsApp is **not automated** — its channel adapter deliberately leaves the notification `PENDIENTE` for an assisted inbox in the admin where Manu clicks a prefilled `wa.me` link. Swapping in WhatsApp Cloud API later means implementing `send()` in `lib/notifications/channels/whatsapp.ts` and flipping its `sendsAutomatically` flag; nothing else changes.

Nothing is sent inline from a Server Action. `createBookingRequest` **enqueues** into the `notifications` outbox and a worker dispatches, so a Resend outage can never break a booking. Two distinct protections against duplicates: a unique index on `dedupe_key` (guards *enqueueing*) and an atomic claim — `update ... where status='PENDIENTE' returning` (guards *sending*; the index alone is not enough, since two bookings seconds apart each trigger a dispatch that reads *all* pending rows).

Reminders and birthdays run off one daily Vercel cron (`vercel.json`, `0 13 * * *` = 08:00 Bogotá; the Vercel dashboard displays schedules in UTC). It authenticates with `CRON_SECRET`, which takes precedence whenever it is set — trusting the `x-vercel-cron` header first would let anyone forge it off-Vercel. `/api/cron/*` is the **only** HTTP route in the project; everything else is Server Actions, and it's outside `middleware.ts`'s `/admin/:path*` matcher.

The birthday message is marketing, not transactional: it respects `clients.marketing_opt_out` (Ley 1581, Habeas Data) and carries an unsubscribe line. Booking and reminder messages are transactional and always send.

Email templates live in `notification_templates` (editable from the panel) and are rendered by `lib/notifications/templates.ts`, which **escapes HTML in interpolated values and strips CR/LF from the subject** — those values come from a public form. The email header logo is `notification_settings.email_logo_url`, a **separate column from `site_settings.logo_url` on purpose**: the site logo is an SVG and no major email client renders SVG in an `<img>` (Gmail and Outlook block it), so emails need their own PNG/JPG asset.

Without `RESEND_API_KEY`/`RESEND_FROM`/`CRON_SECRET` the whole app still works; email notifications just land as `OMITIDO` with the reason visible in the panel's history. Those three are set **only in Vercel's Production environment**, so Preview deployments degrade that way by design.

## Architecture notes

- **Next.js config (`next.config.mjs`)** intentionally ignores ESLint and TypeScript errors during `build` (`ignoreDuringBuilds` / `ignoreBuildErrors`), and disables Next's image optimization (`images.unoptimized: true`). All images/video live in Supabase Storage (bucket `site-media`, whitelisted via `remotePatterns`) — **Cloudinary has been fully retired**, don't reintroduce it. `experimental.serverActions.bodySizeLimit` is raised to `20mb` (default 1MB is too small for the short video clips the CMS allows uploading).
- **Auth**: Supabase Auth, single admin user, no roles — any authenticated user has full access via RLS (`admin_full_access` policy, `for all to authenticated using (true)`) on every admin-managed table. `middleware.ts` + `app/admin/(dashboard)/layout.tsx` gate `/admin/*`. Content tables (`hero_slides`, `service_categories`, `gallery_images`, `promotions`, `site_sections`) additionally grant public read of active rows to `anon` — a deliberate exception to the rest of the app, which never lets the public read with the anon key (public writes go through Server Actions using the service-role client instead, e.g. `app/reservar/actions.ts`, `app/promo-actions.ts`).
- **Timezone**: everything is `America/Bogota`, fixed `UTC-5`, via the helpers in `lib/booking/timezone.ts` (`bogotaWallTimeToUtc`, `toBogotaWallClock`, `nowInBogota`, `todayInBogota`, …). The Vercel process runs in **UTC**, so never use local getters (`getHours`, `getDate`), `Intl`, or `date-fns` with local time for business logic. The admin calendar is the subtle case: `components/admin/agenda-calendar.tsx` runs FullCalendar with `timeZone='UTC'` and paints every event as Bogotá wall time disguised as UTC (`toFakeUtcIso`), so it must also be handed a `now` function on the same fake-UTC scale — otherwise the `nowIndicator` line and the "today" highlight sit 5 hours ahead. (One deliberate exception: the `format(date,'yyyy-MM-dd')` calls on `react-day-picker` values are client-side and correct as they are — that Date is local midnight, so local getters round-trip it exactly.)
- **Analytics**: Google Analytics is wired manually rather than via a library. `lib/gtag.ts` exposes `pageview`/`gaEvent` helpers that call `window.gtag`. `app/layout.tsx` injects the GA script tags only when `NODE_ENV === 'production'` and `NEXT_PUBLIC_GA_ID` is set, with `send_page_view: false` so pageviews are tracked manually. `app/ga-listener.tsx` is a client component (wrapped in `Suspense` in the layout, required because it uses `useSearchParams`) that calls `pageview()` on every route/query change.
- **Styling**: Tailwind, configured via `components.json` (shadcn/ui conventions, `baseColor: neutral`, no class prefix). Brand colors (`brand.ink`, `brand.sand`(+light/dark), `brand.teal`(+light/dark)) are defined in `tailwind.config.ts` as `hsl(var(--brand-*))` — **not hex literals** — so they can be re-themed at runtime; see "Theming" below before assuming a color is static. Section headings across the redesigned components use `font-display italic` (Playfair Display) for an editorial feel; body/nav text stays on the sans stack (Montserrat). Note there are two global stylesheets — `app/globals.css` (used by the app, referenced by `components.json`, holds the `--brand-*` default HSL values) and `styles/globals.css` — check which is actually imported before editing global styles.
- **Theming (colors)**: the 3 base brand colors (ink/sand/teal) are optionally overridden per-deployment from `site_settings.theme_ink/theme_sand/theme_teal` (hex, nullable — `null` = use the `globals.css` default). `app/layout.tsx` (root layout, wraps `/admin` too) injects a `<style>` override built by `lib/theme/colors.ts`, which derives the light/dark variants automatically from the 3 base hex values. Editable from `/admin/contenido` → Sitio → "Colores de marca", with a reset-to-default button. Individual `site_sections` (editorial home blocks) additionally carry their own independent `bg_color`/`text_color` — two separate layers of color customization, don't conflate them.
- **UI components**: `components/ui/` holds shadcn-style primitives (`button.tsx`, `card.tsx`, `input.tsx`, `tabs.tsx`, `dialog.tsx`, etc.) plus one custom primitive, `AnimatedButton.tsx`, used across sections as the "Reservar cita" CTA. It renders a `motion.a`: if given a `phone` prop it builds a `wa.me` WhatsApp deep link (with a prefilled `message`), otherwise it links to `href`. Path alias `@/*` maps to the repo root (see `tsconfig.json` / `components.json` aliases).
- **Animation**: Framer Motion is used throughout, with a shared cubic-bezier ease (`EASE_OUT`, defined both as a local const per-file and centrally in `lib/constants.ts`). Common pattern: a `headerContainer`/`headerVariants` for section titles animated with `whileInView`, and a `cardItem` variant applied per-card with `custom={index}` for staggered delays. `useReducedMotion()` / `prefers-reduced-motion` is checked before applying hover/tap/zoom motion in several components. Admin drag-to-reorder lists (hero slides, service categories, gallery images, home sections) use Framer Motion's `Reorder.Group`/`Reorder.Item` with `useDragControls` (a dedicated grip handle, not the whole row) — not dnd-kit or any other DnD library.
- **Hero carousel** (`components/hero-carousel.tsx`): Embla (`embla-carousel-react` + `embla-carousel-autoplay`, versions pinned exactly in `package.json` — a version mismatch between them previously broke the build, don't let them drift apart again) handles swipe/dots/arrows navigation; slide data comes from `hero_slides` (image or short video). Framer Motion layers on top for a continuous Ken Burns zoom (alternating zoom-in/zoom-out by slide index parity) and a staggered text reveal (alternating entrance direction) re-triggered on every slide change, not just on mount.
- **Gallery**: `gallery_images` (with a free-text `category` field) drives both `components/gallery-preview-section.tsx` (first 3 active images, dark background, shown on the home) and the full filterable experience at `/galeria` (`components/gallery-section.tsx`, category filter + `yet-another-react-lightbox`, loaded via `next/dynamic` with `ssr: false` since it isn't SSR-safe).
- **Home page composition**: `app/page.tsx` does **not** hardcode section order in JSX. It fetches all `site_sections` (ordered by `display_order`), and for each row switches on `kind` to render the right component — `'editorial'` rows carry their own content (photo/video/solid-color background + text), while `'services'/'about'/'mission_vision'/'gallery'` are marker rows with no content of their own (that still lives in `service_categories`/`site_settings`/`gallery_images`) whose only purpose is letting the admin interleave/hide those fixed sections via the same drag-and-drop list. Hero and Footer are not part of this list (always first/last). See `docs/REFERENCIA-CMS-Y-ADMIN.md` for the full model.
- Content (slides, services, gallery images, promotions, site settings, editorial sections) is **not** hardcoded — it's fetched server-side from Supabase with `revalidate = 60` (ISR) plus `revalidatePath()` calls from the relevant Server Actions for instant reflection after an admin edit. Don't add hardcoded copy/images back into a component; add a row/field in the CMS instead and wire it through props, following the existing pattern in any of the CMS-driven components.
